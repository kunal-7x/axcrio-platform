If I were leading this, I would stop building infrastructure that already exists and turn the project into a composition layer: self-host the pieces that are strong, use vendor APIs where they already exist, and only write custom code for the business logic that makes your product unique.

What I would standardize on

1) Workflow automation:
Use n8n as the automation backbone. It is designed for workflow automation, can be self-hosted, exposes a public REST API, and even ships a self-hosted AI starter kit for building AI workflows quickly. 

2) Durable orchestration:
Use Temporal for the things that must never silently break: call follow-ups, WhatsApp sequences, retry logic, approvals, campaign launches, and long-running automations. Temporal is open source, is built for durable execution, and has a self-hosted service guide. 

3) Knowledge / retrieval:
Use Qdrant for campaign knowledge, product knowledge, objection handling, and RAG. Qdrant is an open-source vector search engine with live updates and hybrid retrieval, and it supports self-hosted deployment. 

4) Realtime voice / media layer:
Use LiveKit for the realtime voice-agent side instead of rebuilding your own media stack. LiveKit is open source, supports self-hosting, and its agents framework is built for realtime multimodal/voice agents. 

5) Model serving:
Use Ollama for local model access when you want simplicity, and vLLM when you need higher-throughput serving. Ollama runs locally and can keep prompts/data on your machine; vLLM is an open-source LLM serving library with an OpenAI-compatible API server and streaming support. 

6) Core database:
Use PostgreSQL as the source of truth for tenants, users, leads, campaigns, permissions, audit logs, billing ledger, workflows, and settings. PostgreSQL is a powerful open-source object-relational database, and it is designed for complex data workloads. 

7) Cache / queues / fast state:
Use Redis for low-latency state, caching, streams, and event fan-out. Redis is an open-source in-memory data structure store used as a cache, message broker, streaming engine, and more.

What I would not build from scratch

I would not build custom versions of:

a workflow engine,

a realtime voice/media platform,

a vector database,

a model-serving layer,

or a durable job orchestration system.


Those are exactly the kinds of things that burn months and still end up weaker than battle-tested open-source platforms.

Execution plane

Open-source infrastructure does the heavy lifting:

Qdrant handles retrieval. 

LiveKit handles realtime voice. 

Ollama / vLLM handle model serving. 

PostgreSQL + Redis handle the product data and fast state.

The execution rule I would enforce

Every new idea must be answered with one of three decisions:

1. Reuse an existing OSS system.


2. Integrate an external API.


3. Custom-build only the missing business logic.



That keeps the work feasible and prevents a second “three months wasted on infrastructure” situation.
